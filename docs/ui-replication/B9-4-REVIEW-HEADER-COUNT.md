## 二、三个数的精确定义

复用 `QuestionRepository.reviewBucketOf`（`lib/data/repository.dart:30`）
的共享口径，不另发明计数。一道题按其**全部**错因记录互斥分类，
只落一个桶：

| 页顶数 | 定义（按题数） | 与角标 / 首页的关系 |
|---|---|---|
| 待解决 / 解决中 | 桶为 `pending` 的题数（≥1 个错因未解决，含解决中） | = 首页焦点卡“待解决”数 |
| 复查 | 桶为 `recheck` 的题数（全部已解决且 ≥1 条到复查时间） | = 首页焦点卡“复查”数 |
| 已解决 | 桶为 `solved` 的题数（全部已解决且无一条到复查时间） | = 错题本封面三数第三项（同口径） |

三数互斥相加：待解决 + 复查 = 角标数 = `dueToday().length`
（首页焦点卡总数）；已解决是第三项，不计入要复习总数。
`_metaCounts` 仍不过滤（与改前一致，HTML `revListHTML` 口径）。

### 为什么不会双计 / 漏计——`_groups` / `_curedGroups` 的建法

`_load()` 里每条记录按 `isPending = status != solved || isRecheckDue`
分流，只进 `_groups` 或 `_curedGroups` 其中一边：

- 一题多错因、状态不一时，该题**同时出现在两边**（例如错因 A
  已解决进已解决区、错因 B 待解决进待治区；或 A 已解决未到复查
  进已解决区、B 已解决已到复查进待治区）。这是按记录分组的
  展示结构，不是按题的计数结构——直接数两边的记录数就是旧口径
  的错因条数。
- 新 `_metaCounts`（`review_page.dart:407–441`）先把两边的
  `_CauseItem` 按题汇总（`byQ[questionId]`），每题的记录集就是
  该题的**全部**记录（每条记录恰好出现一次，无遗漏、无重复），
  再对每题调一次 `reviewBucketOf` 算桶、三数各加一。多错因一题
  只计 1 道；已解决区的题不会同时计入待解决区。
- 已归档题不进两边（`_load` 的 `q.isArchived` 跳过），与角标 /
  首页口径一致（取消归档后重新计入）；无记录的题两边都没有，
  桶为 `none`，三处都不计（`switch` 里 `none` 直接跳过）。

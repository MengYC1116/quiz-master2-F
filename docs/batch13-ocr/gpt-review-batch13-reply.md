## 二、P1：候选机制没有充分保证候选与原切片版本绑定

这是本批我认为最重要的数据正确性风险。

### 2.1 目前方案已经做对的部分

以下设计是正确的：

- OCR 自动应用前检查切片 hash。
- 检查题目是否仍然存在。
- 检查领取任务时的 content_version。
- 自动应用时 content_version + 1。
- 人工编辑保存时 content_version + 1。
- 手动编辑后的题干不允许被迟到结果自动覆盖。
- 用户接受候选前可以预览新旧内容。
- 不通过文本相等比较判断候选是否存在。

尤其是最后一点：不能通过文本内容是否相等判断候选是否存在。两次识别可能得到完全相同的文字，但它们仍可能是两个不同的任务结果。

### 2.2 目前存在的漏洞

你现在的关键逻辑是：ocr_raw 恒写最新原始结果，JSON 内含 has_unseen_candidate；ocr_stem 只在安全时写；hasPendingOcrCandidate() 只读取标志。

问题在于：候选标志只回答“有没有候选”，不回答“这个候选来自哪张图、属于哪个任务、是否仍然有效”。

举一个实际竞态：

1. 任务 J1 对切片 H1 开始 OCR。
2. 用户重新框选，切片变为 H2。
3. 新任务 J2 入队。
4. J1 迟到返回。
5. H1 与当前 H2 不一致，因此 J1 不应该自动写入 ocr_stem。
6. 但按当前描述，J1 的原始结果仍会写入 ocr_raw，并可能设置 has_unseen_candidate=true。
7. 用户看到“有新的识别结果”，预览并接受。
8. 如果接受操作没有重新验证候选对应的输入 hash，J1 的旧内容就可能被写入当前题目。

这就出现了一个重要区别：

- content_version 不一致：可能只是用户人工编辑了题干，原切片仍然相同；候选可以保留给用户比较。
- input_hash 不一致：说明候选来自另一张切片；它不能作为当前切片的正常候选直接接受。

这两种情况不能都简单处理成 has_unseen_candidate=true。

另外，ocr_raw 被后续结果覆盖时，如果用户尚未处理之前的候选，旧候选可能丢失。一个布尔标志不能管理多个不同任务产生的候选。

### 2.3 修法

我建议至少把候选包变成有来源身份的信息：

```
candidate:
  job_id
  question_id
  input_hash
  claimed_content_version
  created_at
  raw_result
```

其中 candidate_status 至少区分：

- pending：等待用户处理
- accepted：用户已接受
- ignored：用户已忽略
- stale：切片已经变化，不再适用于当前题目

应用规则：

| 情况 | 是否自动写入题干 | 是否可作为有效候选 |
|---|---|---|
| hash 相同，版本相同，未人工编辑 | 是 | 不需要候选 |
| hash 相同，版本不同，用户已人工编辑 | 否 | 是 |
| hash 不同，切片已变化 | 否 | 否，应标记 stale |
| 题目已删除 | 否 | 否 |

用户点击“接受候选”时，必须重新确认：

1. 题目仍然存在。
2. 候选的 input_hash 与当前切片一致。
3. 候选仍处于 pending 状态。
4. 候选没有已经被接受或忽略。

不要求接受候选时 content_version 仍等于 OCR 领取时的版本。因为用户人工修改过题干、但切片没变化时，正是需要允许其比较并主动接受新结果的情形。

### 2.4 还必须保证检查和写入是原子的

你说明了“应用前必查三项”，但没有明确说明三项检查与 ocr_stem 写入是否在同一个 SQLite 事务中。

如果是：

```
读取 content_version
检查 hash
确认题目存在
等待其他异步操作
更新 ocr_stem
```

那么仍然存在竞态：

- OCR 线程读到版本 7。
- 用户编辑保存，将版本更新为 8。
- OCR 线程仍然使用之前的检查结果写入。
- 人工编辑被覆盖。

修法是：

- 切片路径采用不可变版本文件，避免 hash 校验后文件又被替换。
- hash 核验完成后，在数据库事务内完成任务状态核验、版本比较和条件写入。
- 更新时使用 WHERE question_id = ? AND content_version = ? AND ocr_manual_edited = 0 这类条件更新。
- 必须检查实际更新行数；不是 1 行就不能认为自动应用成功。
- 领取任务和完成任务也应有任务身份或租约 token，避免过期 worker 完成任务时影响新领取者。

P1 在候选来源绑定、候选接受时复核 hash，以及检查与写入的原子性得到证明前，M3 候选机制不能 PASS。

## 三、M3 队列：总体 PASS，没有发现确定的死任务设计

你这次队列比早期方案完整很多。

### 3.1 租约与超时

- 请求超时：120 秒。
- 租约：5 分钟。
- 单 worker、并发 1。
- 超过租约后可恢复任务。

这组参数本身没有明显冲突。正常情况下，单次请求会在租约过期前结束。

建议确保任务完成时还要验证当前领取者的 lease token，避免设备休眠、进程恢复或者另一个实例重新领取任务后，旧 worker 仍然提交结果。

另外，Dart Future.timeout 本身不等于底层 HTTP 请求已经取消。必须确保超时路径会 abort/close 对应的 HttpClientRequest，避免超时后旧网络请求仍继续占用连接或产生重复计费。

### 3.2 重试和失败分类

PASS

目前的分类合理：

- 网络断开、连接超时、请求超时、429、5xx：允许重试。
- Key 无效、权限错误、参数错误、图片损坏、文件不存在：不重试。
- 最多 4 次总请求。
- 退避 30→60→120 秒。
- 429 优先遵守 Retry-After。

GLM-OCR 官方 MaaS 配置也使用这个接口和模型名称，并将 429、500、502、503、504 作为默认重试状态码。官方配置的请求超时默认 300 秒；你的 120 秒是更严格的应用侧限制。

### 3.3 没有 API Key 是否会形成死任务？

不会因为你当前的设计必然形成死任务。

没有 Key 时：

- 不发请求。
- 不增加 attempt。
- 不进入 failed。
- 延迟后重新检查。
- 保存 Key 后调用 kick()。

这是合理的等待状态，而不是失败状态。

但我建议确保保存 Key 后的 kick() 会使等待 Key 的任务立即变为可领取状态，或者明确让 worker 在收到 kick 时忽略原来的 10 分钟延迟。否则只是唤醒 worker、但 available_at 仍在未来，任务可能还会等待到原定时间。

这属于需要验证的唤醒行为，尚不能据此认定死任务。

## 四、M4 题干切分：PASS，但歧义结果必须保持待确认语义

### 4.1 切分算法

PASS

我认可当前的保守策略：

- 支持多种 A–E 标记。
- A→B 顺序明确才切。
- 标记格式需要一致。
- A 需要处于合理的选项起始位置。
- B 必须在 A 后两行内出现。
- C/D/E 是辅助证据，不是必要条件。
- 只出现 A 不切。
- 多个候选切分点不自动选取。
- ①②③④、(1)(2)、填空括号不参与切分。
- 不盲目删除开头数字题号。

这套规则比简单找第一个 A 稳健得多。

### 4.2 歧义状态会不会把选项混进题干？

会。

当 splitStem 判定为“存在歧义”时，整段文本被保留。因此，如果原始文本中包含选项，选项就可能出现在 ocr_stem 的显示内容中。

这不是数据丢失，反而是保守策略的预期结果。你也明确接受了双栏听力题一框包含两道题时，先保留全文。

我不把这种保留策略本身定为 P1。

但有一条必须满足：ocr_split_status = 存在歧义 时，界面不能把它显示成已经成功分离的“题干”。

应该显示类似：

识别结果待确认
“识别内容包含无法确定的选项边界，请检查题干内容。”

如果当前 M5 的七态状态直接将它显示为普通的“识别完成”，没有任何歧义提示，那才是需要修正的明显错误逻辑。建议将 ocr_split_status 作为独立内容状态展示，不要混进队列的七态状态里。

## 五、M5 编辑刷新守门：PASS；重框自动入队：P1

### 5.1 表单刷新守门

PASS

你描述的规则正确：

- 当前正在编辑的题目收到 OCR 事件，不调用 refresh()、loadForm() 或 load()。
- 当前编辑器只读取候选状态，并显示新候选横幅。
- 其他题目的事件，只更新 OCR 状态行。
- 不改变表单值。
- 不改变 formResetKey。

这对防止 OCR 结果异步返回时覆盖用户正在编辑的表单非常重要。

41 个新增测试如果确实覆盖了当前编辑题、其他题目、OCR 完成、失败、候选出现和保存等事件路径，足以支持当前 PASS。

还应确认详情页和整理工作台使用的是同一份编辑守门逻辑，而不是只有工作台做了保护。

### 5.2 详情页重新框选成功后 fire-and-forget 创建任务

P1

这条我不建议保留为当前描述的形式。

需要区分两个动作：

- 创建持久化任务：必须确认数据库插入成功。
- 唤醒 worker：可以 fire-and-forget。

如果 enqueueOcrJob() 本身也是 fire-and-forget，就会有这样的路径：

1. 用户重新框选成功。
2. 新切片保存成功。
3. 创建 OCR 任务的数据库操作异步执行。
4. 数据库写入失败、数据库关闭或进程退出。
5. 页面已经表现为重新框选成功。
6. 实际没有任务记录，也没有用户可见的入队失败状态。

这就是静默丢任务。

修法：

1. 新切片先写入临时文件，成功后原子重命名为不可变版本文件。
2. await enqueueOcrJob()，确认任务已持久化。
3. 成功后再 fire-and-forget worker.kick()。
4. 入队失败时，保留已经成功的框选结果，但明确显示“题目已更新，OCR 未入队”，提供重试入口。
5. 不要让页面把“框选成功”错误地等同于“OCR 已排队”。

数据库任务记录是持久化队列的可靠性边界，不能把它当作普通后台通知。
